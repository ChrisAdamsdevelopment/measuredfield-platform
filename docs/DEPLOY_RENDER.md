# Render deployment runbook

Companion to `DEPLOYMENT_READINESS.md` (gates and constraints). This is the step-by-step.
Nothing here has been executed: no Render service, database, domain or DNS record exists
for MeasuredField yet. Use a **new Render workspace**, separate from Prescott's Best
Construction, and do not touch PBC hosting or DNS.

**Needs your approval before doing it:** every step marked 💲 creates a paid resource.

## Target layout

| Resource | Type | Notes |
|---|---|---|
| `measuredfield-staging-db` 💲 | Render PostgreSQL 16 | Own database. Daily backups / point-in-time recovery depend on plan; choose one that includes PITR before real customer data. |
| `measuredfield-staging-web` 💲 | Web service, native Python 3.12 | `render.yaml`. Health check `/healthz`. Pre-deploy runs migrations. |
| `measuredfield-staging-worker` 💲 | Background worker | `python -m app.worker`. Can be skipped at first by setting `MF_INLINE_JOBS=true` on the web service (single instance only). |
| Production | Same three, separate names and database | Copy the blueprint with `production` names and `MF_ENV=production` once staging passes the gates. Never share a database between staging and production. |

Static assets are small and served by the app with cache headers. Putting Cloudflare in
front for DNS, TLS and edge rate limiting is recommended before public launch; it is not
required to run.

## 1. Repository (already published)

**Canonical public repository:** https://github.com/ChrisAdamsdevelopment/measuredfield-platform

This repository is intentionally PUBLIC because the owner has experienced Render's
GitHub repository-picker failing to show private repositories in this workspace.
Connect this exact repository to Render, selecting branch `main`. The
`render.yaml`, application code and Dockerfile are now present on GitHub.

Do NOT run `git init` or `git add -A` again in the shared canonical checkout.
Multiple agents work in the same Git main; stage only claimed files. Before each
public push, run the tracked/staged secret scan and check current plus historical
Git blobs. CI (`.github/workflows/ci.yml`) exercises PostgreSQL isolation tests.

**Do not create a running public customer service yet:** staging requires
separate runtime/migration database roles, secrets, host configuration and security
preflight. GitHub visibility and application deployment readiness are separate.

## 2. Database and the two roles

1. Create the Render PostgreSQL instance 💲. Its default user becomes the **owner /
   migration** role.
2. Connect as that user (`psql` from the Render dashboard's external URL) and create the
   **runtime** role with a password you generate and store in a password manager:
   ```sql
   CREATE ROLE mf_app LOGIN PASSWORD '<generated>' NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE;
   ```
3. Build two connection URLs from the instance's **internal** hostname:
   * `MIGRATION_DATABASE_URL` = owner user
   * `DATABASE_URL` = `mf_app`

## 3. Blueprint

Render dashboard → New → Blueprint → select the repository. It reads `render.yaml` and asks
for the values marked `sync: false`:

| Variable | Value |
|---|---|
| `DATABASE_URL` | the `mf_app` URL (web **and** worker) |
| `MIGRATION_DATABASE_URL` | the owner URL (web only; used by the pre-deploy step) |
| `MF_APP_HOSTS` | e.g. `staging.example.com,measuredfield-staging-web.onrender.com` |
| `MF_SITES_BASE_DOMAIN` | e.g. `sites.example.com` |
| `MF_PUBLIC_BASE_URL` | e.g. `https://staging.example.com` |

`MF_SECRET_KEY` is generated by Render and shared with the worker. Auto-deploy is off.

## 3A. If creating an individual New Web Service (owner's current path)

Choose **New Web Service**, not Static Site or Private Service. Connect GitHub
repository `ChrisAdamsdevelopment/measuredfield-platform`, branch `main`.
Keep Root Directory empty.

| Render field | Setting |
|---|---|
| Runtime | Python 3 |
| Region | Oregon (same as the staging Postgres instance) |
| Name | `measuredfield-staging-web` |
| Build command | `pip install -r requirements.txt` |
| Pre-deploy command (paid tier) | `python -m app.migrate` |
| Start command | `python -m uvicorn app.main:app --host 0.0.0.0 --port $PORT --no-proxy-headers` |
| Health check path | `/healthz` |
| Auto-deploy | Off; deploy only after manual review |

Set `PYTHON_VERSION=3.12.10`, `MF_ENV=staging`, `MF_PAYMENT_PROVIDER=none`,
`MF_EMAIL_PROVIDER=none`, `MF_AI_PROVIDER=none`, and `MF_TRUST_PROXY_HEADERS=false`.
For one Web Service with **no worker**, set `MF_INLINE_JOBS=true` and keep one
instance; do not use the Blueprint's `MF_INLINE_JOBS=false` value until the worker exists.
Also configure `DATABASE_URL` (restricted `mf_app` role), `MIGRATION_DATABASE_URL`
(owner role), `MF_SECRET_KEY` (random >=32 chars), `MF_APP_HOSTS` (exact Render
hostname), `MF_PUBLIC_BASE_URL` (https origin), `MF_SITES_BASE_DOMAIN`
(real, non-overlapping customer-site domain), and `MF_TRUSTED_PROXY_HOPS=0` until
the proxy chain can be verified. Never commit environment values.

**First boot trap:** the migration owner creates schema objects, but the restricted
runtime role initially lacks grants. Run the SQL grant script as schema owner
after the first migration, then restart the web service. Do not simply give the
runtime role superuser or BYPASSRLS privileges to make boot succeed.
Until the verified proxy hop count and edge rate limiting are in place, keep
this service staging-only, not ready for unrestricted customer traffic.

## 4. First deploy

1. Deploy the web service. The pre-deploy command `python -m app.migrate` applies
   migrations as the owner.
2. Once, as the owner, run `scripts/grant_runtime_role.sql` (grants `mf_app` table access
   and default privileges for future tables).
3. Restart the web service. In staging/production it **refuses to start** if its role can
   bypass row-level security, if any tenant table lacks forced RLS, or if the secret key,
   base URL or hosts are unsafe. Read the deploy log if it exits.
4. From the web service shell:
   ```bash
   python -m app.cli isolation-check
   MF_OPERATOR_PASSWORD='<generated>' python -m app.cli create-operator you@yourdomain
   ```
5. Open `https://<app host>/readyz` (expect `{"status":"ready"}`), then sign in at `/login`.

## 5. Domains and HTTPS

* **App host**: add the custom domain to the web service in Render; create the CNAME Render
  shows. Render issues and renews the certificate.
* **Customer subdomains** (`<slug>.<MF_SITES_BASE_DOMAIN>`): add the wildcard domain
  `*.sites.example.com` to the same web service and create the wildcard DNS record Render
  specifies. Verify on Render's current docs that your plan supports wildcard custom domains.
* **A customer's own domain**: the owner requests it in Website → Addresses; add that
  hostname to the web service in Render, have the customer create the DNS record, wait for
  the certificate, then click **Verify** in the operator console. Until then the hostname
  serves nothing.

## 6. Client address behind the proxy (verify before launch)

Rate limits key on the client address. By default the app uses the socket peer, which
behind Render is the proxy, so **all visitors share one bucket** (sign-in is limited to 20
attempts per 15 minutes in total). To fix this correctly, find out how many trusted proxies
append to `X-Forwarded-For` on your setup: from two different networks, request a page and
read the app's view of the header (temporarily log it, or use Render's request logs), sending
a forged `X-Forwarded-For: 1.2.3.4`. The number of entries **after** your forged one is the
hop count. Set `MF_TRUSTED_PROXY_HOPS` to it (commonly 1 for Render alone, 2 with Cloudflare
in front) and confirm the forged value is ignored. Leave it at 0 if unsure.

## 7. Turning providers on (each is a separate decision)

| Capability | Set | Then |
|---|---|---|
| Email | `MF_EMAIL_PROVIDER=resend`, `MF_RESEND_API_KEY`, `MF_EMAIL_FROM` (a verified sender domain) | Invite yourself; confirm the outbox row reads `sent` with a provider id. |
| Payments | `MF_PAYMENT_PROVIDER=stripe`, `MF_STRIPE_SECRET_KEY`, `MF_STRIPE_WEBHOOK_SECRET`; add a Stripe webhook endpoint `https://<app host>/webhooks/stripe` for `checkout.session.completed` | Run one order end to end in Stripe **test mode** before any live key. The adapter has only been tested against mocks. |

## 8. Operations

* **Logs**: Render log stream. Request lines contain method, path, status, duration and a
  request id; never query strings, bodies, cookies or addresses. Errors shown to users carry
  the same id.
* **Monitoring**: point an uptime monitor at `/readyz`. Alert on the worker's `job failed`
  log lines and on jobs with status `failed` (operator console shows counts).
* **Rollback**: Render → service → Deploys → Rollback. Migrations so far are additive and
  each has a tested downgrade, but roll the database back only deliberately.
* **Backups and restore drill**: before real data, restore the latest backup into a new
  instance, point a staging web service at it, run `python -m app.cli isolation-check` and
  sign in. This drill has not been performed.
* **Retention**: schedule `python -m app.cli purge` daily (Render cron job 💲 or run it from
  the worker host) to drop expired sessions, tokens and rate-limit windows.
* **Deletion**: an owner schedules workspace deletion in Settings; the worker executes it
  after `MF_DELETION_GRACE_HOURS` (default 72) and writes a receipt to `deletion_receipts`.
